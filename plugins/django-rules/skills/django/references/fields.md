# Django model fields — recommendations

Recommendations for choosing and declaring model fields, choices and status
columns. Prefer these defaults; deviate when a situation genuinely warrants it.

## Field types

1. Prefer semantic `CharField` subclasses defined once — such as those in
   `biased.django.models.char_field`: `DefaultCharField`,
   `DefaultShortCharField` for status and enum columns, `NameField`,
   `DefaultUrlField` — over a raw `CharField(max_length=…)`. Each length is
   then chosen once for its kind of value, and two columns holding the same
   kind of value cannot disagree on it.
2. Subclass those base fields into named field types for domain-specific
   string columns, often in a `models/fields.py`, even when the behavior is
   identical. The type then states what the column holds, and a later change
   to that kind of value — a longer limit, a validator — is made in one class.
3. Store money in one shared money field — such as `DefaultMoneyAmountField`
   in `biased.django.models.default_money_amount_field` — rather than an ad-hoc
   `DecimalField`, and default running totals to `0`. One field fixes
   precision and scale for every amount, so sums and comparisons across tables
   never round differently, and a zero default keeps a new row's total
   summable instead of null.
4. Avoid a bare `JSONField()`. Use a schema-validated field — such as
   `PydanticModelField` in `biased.django.models.pydantic_model_field` — for
   JSON with a known shape, or `JSONField(encoder=…, default=dict)` (or
   `list`) for free-form JSON. A bare field accepts any shape and fails only
   when a reader trips on it; a schema refuses a bad value on write, and an
   explicit encoder and default keep decimals, dates and the empty value
   consistent.
5. Reach for an established library before hand-rolling: an ordered-model
   library for orderable rows, a field-encryption library for sensitive
   columns, phonenumber and localflavor fields for typed values. Their edge
   cases — reordering under concurrency, key rotation, number formats — are
   already solved and tested.

## Choices & status

6. Define choices as `@unique`, string-backed `models.TextChoices` in the app's
   `types.py`, with values generated by `auto()` — not inline in the model
   file. Services, schemas and tests then import the choices without the
   model, `@unique` refuses two members sharing a value, and `auto()` stores
   each member under its own name.
7. Pass the choices class itself (`choices=OrderStatus`), not
   `choices=OrderStatus.choices`: the field then names its type, as an
   annotation would. Django accepts the class from 5.0 on; before that, pass
   `.choices`.
8. Make a status column a `DefaultShortCharField` with `choices=` and an
   explicit initial-state default (`OrderStatus.new`, `OrderStatus.pending`).
   A row is then created in a known state, and a migration adding the column
   has a value for the rows already there.
